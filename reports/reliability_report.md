## 3. Аудит top-K: определения

Реализация — `src/orderpulse/queue_eval.py`, тесты — `tests/test_queue_eval.py` (7 синтетических сценариев с ручной
сверкой: день без задержек, день с n_d < K, одинаковые скоры, дни разного размера, macro/micro, Monte Carlo = аналитике).

- **День** — календарная дата `order_approved_at` в локальных метках времени набора (без перевода часовых поясов).
- **Когорта дня** — заказы выборки (доставленные, с меткой и признаками), подтверждённые в этот день.
- n_d — заказов, m_d — задержек, k_d = min(K, n_d), h_d — задержек среди выбранных.
- precision_d = h_d / k_d; recall_d = h_d / m_d **только при m_d > 0**. Дни без задержек в macro recall не входят
  и нулём не подменяются; их число показывается отдельно.
- micro: Σh_d / Σk_d и Σh_d / Σm_d; macro: среднее precision_d по всем дням и среднее recall_d по дням с m_d > 0.
- Одинаковые скоры на границе K: h_d = задержки строго выше + свободные места · (задержки в группе равных / размер группы).
- Random baseline: равномерный отбор k_d без возвращения внутри дня. Аналитически E[h_d] = k_d·m_d/n_d,
  E[precision_d] = m_d/n_d, E[recall_d] = k_d/n_d (m_d > 0); агрегируется теми же формулами.
  Monte Carlo (500 повторений, seed 2024+K) совпадает с аналитикой: на test@50 MC-среднее 0,0388 при аналитике 0,0389.

### 4.3 Рекомендация по K (по development и ёмкости, не по test)

Lift максимален при малых K и падает к ~1,1–1,3 при K = 100. Предельная полезность LogReg на development:
переход K 10 → 20 даёт +1,52 найденных задержки на 10 доп. проверок (случайно +0,96), 20 → 50 — +3,57 на 30
(случайно +2,89), 50 → 100 — +5,25 на ~48 (случайно +4,75). Выше K ≈ 50 дополнительные проверки почти не лучше
случайных. **Для демонстрации — K = 20 в день** (≈10% заказов). Это демонстрационный компромисс между ёмкостью и lift,
а не доказанный экономически оптимальный размер: стоимость проверки и ценность найденной задержки не известны.
K = 50 оправдан только при наличии такой ёмкости.
Число найденных задержек ≠ предотвращённым: эффект проверки не измерялся. По умолчанию в UI теперь K = 20
(`configs/model.yaml: ui.default_queue_k`).

## 6. Есть ли убедительное преимущество CatBoost

**Нет.** На ранее просмотренном test CatBoost и LogReg статистически неразличимы: все интервалы разницы включают 0.

В проверенном development-протоколе (3 окна, фиксированные параметры v1, одинаковые заказы):
- **Precision@K (K = 10, 20, 50):** устойчивое преимущество LogReg. Интервалы разницы ниже 0 и при дневных, и при
  недельных блоках. LogReg выше и в каждом окне по отдельности (точечные оценки, раздел 4.1).
- **AP:** дневной bootstrap поддерживает преимущество LogReg (−0,011 [−0,019; −0,004]), недельный интервал включает 0
  (−0,012 [−0,029; +0,001]). Значимость по AP не утверждается.
- CatBoost нестабилен в этом протоколе: в 4 из 9 обучений early stopping на одномесячном окне выбрал 0–2 итерации,
  то есть почти константную модель (`ablation_dev.csv`, `best_iteration`). LogReg обучается за ~0,5 с против 6–25 с
  и не зависит от early stopping.

Вывод относится к **конкретным проверенным конфигурациям** (параметры v1, early stopping по PRAUC на одном месяце).
Он не означает универсального превосходства логистической регрессии над CatBoost: другой протокол обучения
CatBoost (без ранней остановки на коротком окне, иная регуляризация) не проверялся.

## 8. Калибровка (условный этап)

Схема: модель W2 (fit 2017-01…08, ES 2017-10) → sigmoid-калибратор на подтверждениях 2017-12 с метками, известными
к 2018-02-01 (5 605 заказов, доля 6,8%) → проверка на 2018-02…03 (13 616 заказов, доля 16,5%).

| На окне проверки | Brier | Logloss | Средний прогноз | Факт |
|---|---:|---:|---:|---:|
| без калибровки | 0,152 | 0,554 | 4,5% | 16,5% |
| sigmoid | 0,142 | 0,467 | 9,9% | 16,5% |
| константа = доля окна калибровки | 0,147 | 0,503 | 6,8% | 16,5% |

Корзины — децили некалиброванного скора на окне проверки, по 1 361–1 362 заказа, 153–316 задержек в корзине.
Фактическая доля во всех децилях 11–23%, калиброванный прогноз — 7–15%. Калибратор улучшает метрики относительно
сырого скора, но **не переносится через сдвиг базовой частоты**: прогноз систематически занижен в 1,7 раза.
Кроме того, при cutoff меток 2018-02-01 70 заказов окна калибровки ещё без метки, и его доля задержек занижена
(6,8% против 7,9% на созревших метках).

**Решение: калибровку в продукт не добавлять, оставить риск-скор для ранжирования.** Это осознанное
ограничение продукта, а не незавершённая обязательная функция: очередь использует только порядок скоров. Честная калибровка требует
пересчёта базовой частоты на свежих исходах (например, скользящей), а она отстаёт на срок доставки.

## 9. История продавцов — нужна ли

Ранжирующая способность на development низкая (ROC-AUC 0,52–0,62 против 0,75 на test). Признаки заказа плохо
объясняют периоды массовых задержек (W3, 16,5%). Point-in-time история продавцов — обоснованный следующий кандидат,
но **на этом этапе не добавлялась**. Требования для отдельного плана:
- агрегаты (число завершённых заказов, доля задержек, медиана длительности за 30/90 дней) считаются только по
  заказам с `label_available_at < prediction_time` текущего заказа;
- ранее купленные, но ещё не доставленные заказы не дают метки; их число можно использовать отдельно, как нагрузку;
- для многопродавцовых заказов — агрегат по основному продавцу и максимум по продавцам;
- холодный старт: индикатор «мало истории» вместо нулей;
- тест: изменение исхода, известного после prediction_time, не меняет признаки;
- оценка на тех же development-окнах (W1–W3) с теми же парными bootstrap-сравнениями.

## 10. Решения и рекомендации

1. **Основная модель v1 не заменена в артефактах.** Рекомендация (по development, не по test): кандидатом v2 сделать
   Logistic Regression — лучше или не хуже на всех окнах, стабильнее, быстрее. Переключение по умолчанию не выполнено:
   SHAP-факторы очереди и карточки реализованы только для CatBoost. Для LogReg нужны линейные вклады — это отдельная задача.
   LogReg v1 уже доступен в очереди через выбор модели.
2. **K по умолчанию в UI — 20 в день** (раздел 4.3).
3. **Календарь:** удаление календарных признаков у LogReg качество не меняет. Для v2 на LogReg допустим вариант C
   как более простой, без сезонных допущений; решение принимать вместе с переходом на LogReg.
4. **Калибровка:** не вводится (раздел 8).
5. **Test:** не перенесён на хвост; июль–август 2018 непригодны как holdout (`dataset_tail_audit.md`).

## 11. Ограничения

- Development-окна до test — 3 окна по 2 месяца, 182 дня. Они пересекаются по обучающим данным: обучение всегда
  начинается с 2017-01. Интервалы bootstrap условны и не учитывают сдвиги будущих лет.
- Параметры CatBoost взяты из v1. Их выбирали на validation (январь–февраль 2018), что пересекается с окнами W2 и W3.
  Это слегка в пользу CatBoost и не меняет вывод.
- Оценка окон использует созревшие метки (раздел 2): ретроспективный, а не real-time выбор.
- Test просмотрен; любые новые сравнения на нём — «ранее просмотренный holdout».
- Механизм формирования конца набора неизвестен (гипотезы — в `dataset_tail_audit.md`). Если отбор существовал,
  он мог затрагивать и ранние периоды; масштаб из этих данных оценить нельзя.

## 12. Уточнения формулировок (релиз v1.0)

1. Преимущество LogReg — устойчивое по Precision@K в проверенном development-протоколе. По AP его поддерживает
   только дневной bootstrap; недельный интервал включает 0.
2. Development-оценка — ретроспективная, по созревшим исходам. Это не полностью воспроизводимый real-time выбор
   на дату 2018-04-01: для W3 часть меток к этой дате ещё не наблюдалась.
3. Для CatBoost проверены конкретные конфигурации; вывод не универсален.
4. Исходный test — ранее просмотренный holdout, а не новый независимый тест.
5. Механизм отбора в конце датасета неизвестен; гипотеза отбора по наличию отзыва не доказана.
6. Доля заказов без отзыва среди включённых не показывает долю отсутствующих заказов в генеральной совокупности.
7. K = 20 — демонстрационный компромисс, а не доказанный экономически оптимальный размер.
8. Найденные задержки — это не предотвращённые задержки: эффект проверки не измерялся.
9. Отсутствие калибровки — осознанное ограничение продукта.
