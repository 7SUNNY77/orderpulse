# OrderPulse — журнал решений

Каждое решение: что выбрано, почему, где реализовано. Фактические числа — из `reports/data_quality.md`,
`artifacts/model_metadata.json` и `artifacts/metrics.json` (fingerprint данных `4179f0f63056937d`).

## D1. Окружение и структура

- **Python 3.11 в `.venv`** (через `uv`), хотя системный Python — 3.14: для 3.14 нет гарантированных колёс CatBoost.
  Проверенные версии зафиксированы в `requirements-lock.txt`, диапазоны — в `pyproject.toml`.
- **Пакет `shap` не используется:** локальные SHAP считает сам CatBoost (`get_feature_importance(type="ShapValues")`).
- **CSV читаются на месте** из `data/` (путь задаётся в `configs/data.yaml`, флагом `--raw-dir` или переменной
  `ORDERPULSE_RAW_DIR`). Каталог `data/raw/` из структуры ТЗ не создаётся, чтобы не копировать 120 МБ пользовательских файлов.
- **`make` в среде отсутствует**: Makefile создан, но не проверен; эквивалент — `python -m orderpulse <команда>` (проверен).
- **Дополнительные модули**, не перечисленные в ТЗ: `config.py`, `utils.py`, `cli.py`, `metrics.py` (чистые функции метрик),
  `models.py` (единый интерфейс четырёх моделей). Каталог `sql/features/` — для SQL прогнозных признаков.
- **Ноутбук `notebooks/exploration.ipynb` не создан**: исследование оформлено воспроизводимыми модулями
  (`quality.py`, отчёты). Ноутбук в ТЗ необязателен для сборки.

## D2. Слои данных и атомарность

- `raw.duckdb`: все значения как текст (`all_varchar`), чтобы ничего не приводилось молча; типизация — в staging через
  `TRY_CAST`, ошибки приведения считаются аудитом (на текущих данных их 0).
- `warehouse.duckdb` собирается **с нуля** во временный файл `*.tmp`, затем выполняются 17 проверок сверки, и только при
  успехе файл заменяет предыдущий (`os.replace`). Повторный запуск даёт идентичные таблицы (тест `test_etl_is_idempotent`),
  сбой оставляет прежнюю базу (тест `test_failed_build_keeps_previous_warehouse`).
- На Windows замена невозможна, пока база открыта запущенным Streamlit; ETL тогда завершается понятной ошибкой,
  а прежняя база остаётся. Перед пересборкой остановите приложение.

## D3. Зерно витрин и защита от размножения

- Позиции, платежи и отзывы **агрегируются до заказа по отдельности**, затем LEFT JOIN к `stg_orders`.
- Измерения (`customers`, `sellers`, `products`, `stg_geo_zip`) проверяются на уникальность ключа до join.
- Проверки сборки: число строк `mart_orders` = числу заказов, нет дублей `order_id`, суммы цен/доставки/платежей и число
  позиций совпадают с источником до копейки (DECIMAL(18,2)), `mart_seller_orders` = числу пар (продавец, заказ).
- Заказы без позиций (775) сохраняются: `items_value = NULL`, а не 0. Заказ с нулевой ценой даёт 0, а не NULL.

## D4. Канонический отзыв

- Ключ отзывов — пара `(review_id, order_id)`: `review_id` сам по себе не уникален (814 повторов).
- У 547 заказов несколько отзывов. Канонический — **последний по `review_creation_date`**, затем по
  `review_answer_timestamp`, затем по `review_id` (по убыванию) — детерминированно.
- Тексты отзывов не интерпретируются; хранится только флаг наличия комментария.

## D5. Многопродавцовые заказы (1 278 заказов)

- Уровень заказа (`mart_orders`): заказ учитывается один раз.
- Уровень продавец–заказ (`mart_seller_orders`): заказ учитывается у каждого продавца; исход заказа (задержка, отзыв)
  приписывается каждому продавцу как **ассоциация, а не вина**. Сумма заказов по продавцам ≠ числу уникальных заказов;
  это подписано в UI.
- Категории: в сегментах — зерно заказ × категория; «основная категория» заказа — с наибольшей суммой цен
  (при равенстве — по имени).

## D7. Словарь метрик

| Метрика | Формула | Когорта / знаменатель | Пропуски | Ось времени |
|---|---|---|---|---|

- Доставка в обещанный календарный день — вовремя, независимо от часа (тест `test_delivery_on_promised_day_is_on_time`).
- 6 отменённых заказов с датой доставки и 8 «доставленных» без даты — **вне** когорты: статус — источник истины,
  отсутствие даты не означает «вовремя».
- Стоимость товаров не называется выручкой или прибылью; стоимость заказов в очереди — не ожидаемый убыток.
- Сверка платежей: совпадают с «товары + доставка» у 98 285 из 98 665 сопоставимых заказов; 380 расхождений
  показаны в UI и отчёте (вероятно, проценты рассрочки), не исправляются.

## D9. Срез данных и неполные исходы

- После **2018-09-03** поток доставок практически обрывается (неделя с 2018-08-27 — 1 607 доставок, следующая — 28),
  покупки заканчиваются ~2018-08-29. У заказов с обещанной датой в сентябре–октябре 2018 доля задержек среди
  доставленных = 0%: поздние доставки просто не попали в набор. Конец набора отобран по исходу.
- Решение: `data_cutoff = 2018-09-03` в `configs/data.yaml`; исходы после него считаются ненаблюдаемыми; test
  заканчивается 2018-06-30. Для заказов, подтверждённых до конца июня, у ≥ 98,5% выполняется условие
  «обещанная дата + 31 день ≤ срез» (31 день ≈ P95 опоздания).

## D11. ML-постановка и доступность признаков

- `prediction_time = order_approved_at`; target — задержка по календарным датам; популяция — подтверждённые
  доставленные заказы с обещанной датой, позициями и без критических временных ошибок (96 395 заказов до разбиения).
- **Модель условна:** она не прогнозирует отмену, потерю или недоставку. Это показано в UI.
- Признаки строятся отдельным SQL (`sql/features/`), который читает только `stg_orders` (покупка, подтверждение,
  обещанная дата), покупателей, позиции, товары, продавцов и геосправочник. X формируется **выбором allow-list**
  (`features.py: FEATURES`, 28 признаков), а не удалением target.
- Допущения доступности (событийного журнала нет): обещанная дата известна при покупке; состав заказа, цены и стоимость
  доставки фиксированы при подтверждении.
- **Исключены из fv1:** платёжные поля (тип, рассрочка, сумма), т. к. нет подтверждения, что таблица отражает
  состояние на момент подтверждения; `shipping_limit_date` (вероятно, вычисляется при подтверждении, но это не
  подтверждено); `seller_id` как признак; исторические агрегаты продавцов (point-in-time не реализован).
- `approval_month` включён по ТЗ. По глобальной важности CatBoost он первый. Это риск: модель может перенести
  сезонность 2017 года на 2018-й. Удалять его по результатам test нельзя; абляция на validation — следующий шаг.

## D12. Модели и выбор

- Константа (доля задержек train), правило «короткий обещанный срок» (score = −promised_days), Logistic Regression
  (медианная импутация + индикаторы, стандартизация, one-hot с `min_frequency=20`), CatBoost (CPU, seed 42).
- CatBoost: сетка из 3 конфигураций, early stopping по validation, выбор по AP на validation (depth=4, lr=0.05, l2=3,
  78 итераций). **Метрика ранней остановки изменена с Logloss на PRAUC** после первого запуска: доля задержек в
  validation (7,4%) выше, чем в train (4,6%), и Logloss останавливал обучение на ~35 итерации из-за сдвига
  базовой частоты, а не качества ранжирования. Решение принято по validation, до получения метрик test.
- Политика проверки: **top-K в день, K = 50** (продуктовое ограничение ёмкости). Порог для precision/recall/confusion
  matrix выбирается на validation так, чтобы доля проверяемых = 50 / средний дневной объём validation = 22,3%.
  На test та же величина порога даёт другую долю (CatBoost 20,6%, LogReg 34,9%) из-за сдвига распределения —
  это показано, а не подстроено.
- Калибратор не обучался: test для этого использовать нельзя, а базовая частота заметно меняется между периодами.
  В интерфейсе — «риск-скор» для ранжирования, не вероятность.

## D13. Top-K по дням

> **Исправлено на этапе 2** (см. D18): равенства скоров и знаменатель lift.

- Когорта — календарный день подтверждения. Внутри дня — сортировка по скору; при равных скорах на границе K
  в метриках берётся ожидание при случайном разрешении (не порядок `order_id`). В отображении очереди равные скоры
  упорядочены по `order_id`.
- Дни с числом заказов < K выбирают все свои заказы (знаменатель precision = фактически выбранные).
- Микро-усреднение — основное (сумма найденных / сумма выбранных или опоздавших); макро-precision — среднее по дням;
  макро-recall — среднее только по дням с ≥ 1 опозданием. Lift — микро-precision / **ожидаемая** микро-precision
  случайного отбора тех же k_d в каждом дне.

## D14. Объяснения и подсказки

- Локальные SHAP CatBoost в пространстве log-odds: базовый уровень + вклады = итоговый raw score; в скор переводится
  только итог (сигмоида), отдельные вклады не переводятся в процентные пункты. Не причинный анализ.
- Для очереди — пакетно вычисленные top-3 признака, повысившие прогноз (в `predict`); полная таблица вкладов —
  по запросу для одного заказа в карточке (кешируется).
- «Подсказки для проверки» — фиксированные правила (`explanations.review_hints`): >1 продавца; обещанный срок < 10 дней;
  риск в top-5% дня; нет координат или характеристик товара.

## D18. Этап 2: исправления оценки (не изменения модели)

- Lift top-K в день теперь делится на ожидание случайного отбора Σk_d·m_d/n_d / Σk_d, а не на общую долю задержек.
- Равные скоры на границе K — ожидание при случайном разрешении. Top-K константной модели равен случайному ожиданию;
  отдельно реализован random baseline (аналитика + Monte Carlo).
- Очередь в UI — top-K **в каждый день** подтверждения (ранее — top-K по всему выбранному диапазону).
- `evaluate` пересчитан; `model.cbm` и `predictions.parquet` не менялись (sha256 совпадают со снимком MVP v1).
- Доступность меток проверяется кодом (`splits.assert_labels_available`) для обучения, early stopping, сетки, порога
  и калибровки. Нарушений в v1 не найдено.

## D19. Этап 2: статус test и решения

- Исходный test (2018-04 … 06) **просмотрен**. Он используется только для описательного аудита фиксированных
  прогнозов v1 и не участвует в выборе. Новые варианты сравниваются на 3 development-окнах до 2018-04-01
  (`configs/reliability.yaml`).
- Test не переносится на хвост: июль–август 2018 непригодны как holdout (`reports/dataset_tail_audit.md`).
  Прежняя формулировка «поздние доставки не попали» уточнена: после cutoff есть 53 опоздавшие доставки.
  Не наблюдается ни одного опоздания среди заказов с обещанной датой ≥ 2018-08-31. Механизм — гипотеза.
- **K по умолчанию в UI = 20 в день** (по development: lift LogReg 1,77 при K = 20 против 1,45 при K = 50;
  выше K ≈ 50 дополнительные проверки почти не лучше случайных). Политика порога v1 (K = 50) в метаданных не менялась.
- **Калибровка не вводится:** sigmoid-калибратор не переносится через сдвиг базовой частоты (прогноз 9,9% при факте 16,5%).
- **Основная модель в артефактах не меняется.** Рекомендация для v2 — Logistic Regression (на development устойчиво
  лучше CatBoost по Precision@K, по AP — только в дневном bootstrap; на просмотренном test разница незначима). Переход требует объяснений для линейной модели
  и отдельного решения владельца.
- Календарные признаки: для LogReg удаление не меняет качество; для CatBoost вывод неопределённый из-за
  нестабильного early stopping.


## D20. Релиз v1.0: Logistic Regression — основная модель

- **Решение владельца:** основная модель интерфейса — существующая Logistic Regression v1 (`logreg-fv1-77259041`),
  CatBoost v1 остаётся для сравнения; K = 20 в день (`configs/model.yaml: ui.default_model`, `ui.default_queue_k`).
- Модели и прогнозы **не переобучались** для смены основной модели: используются те же `logreg.joblib` и
  `predictions.parquet` (sha256 — `docs/release_checklist.md`).
- Выбранная модель хранится в `st.session_state["op_model"]` и общая для очереди и карточки. Карточка, открытая
  из очереди, показывает скор, ранг и объяснение той же модели. Смена модели в карточке меняет и модель очереди.
- **Объяснения LogReg** — линейные вклады: decision_function = intercept + Σ coef_j · z_j по фактическому
  `ColumnTransformer` (130 колонок). Вклады one-hot и индикаторов пропуска агрегируются до 28 исходных признаков.
  Объяснения CatBoost (SHAP) показываются только для CatBoost. Для baselines объяснения нет.
- Факторы в очереди: для LogReg вычисляются по запросу для показанных строк (та же модель, кешируются);
  для CatBoost — сохранённые SHAP top-3.
- Не меняется: признаки (календарные остаются), временные выборки, калибровка (нет), история продавцов (нет).

## D21. Правила очереди релиза

- Фильтры (штат, основная категория, многопродавцовые) применяются **до** выбора top-K. В каждый день
  подтверждения выбираются K заказов с наибольшим скором среди отфильтрованных; за диапазон из d дней строк до K·d.
  Отфильтрованная очередь — это политика внутри сегмента: её метрики показываются с предупреждением и не
  сравниваются с общими метриками модели.
- Равные скоры в таблице упорядочены по `order_id` (детерминированно; метки не используются). В метриках ties
  учитываются ожиданием при случайном разрешении — у LogReg и CatBoost ties практически отсутствуют, у константы
  метрика равна случайному ожиданию, а таблица — фиксированной перестановке.
- CSV-экспорт — та же таблица, что на экране (включая столбец версии модели и, если включены, исходы).
- Ранг в таблице очереди считается после фильтров; ранг в карточке — среди всех заказов дня.
- Лицензия кода не выбрана: указание MIT, добавленное на этапе MVP без согласования, удалено.
