## 2. Выполненные проверки

**Тесты:** `python -m pytest` → **81 passed** на момент релиза; после подготовки к публикации добавлены 4 теста CLI → **85 passed** (раздел 7). Среди них:
- 7 тестов линейных объяснений LogReg: сумма = `decision_function`, агрегация сохраняет сумму, неизвестная
  категория, пропуски как в обучении, класс 1 = опоздание, совпадение с показанным риск-скором;
- 5 ручных тестов очереди: несколько дней и моделей, фильтр до top-K, ties, дни с n < K;
- UI-тесты через Streamlit AppTest: LogReg и K = 20 по умолчанию, top-K по дням на диапазоне, карточка с моделью
  из очереди и переключение модели, пустая выборка, исходы и случайный baseline, отсутствующие артефакты и база.

**Линейные объяснения на реальных данных** (2 000 заказов): |intercept + Σвкладов − decision_function| = 0,0;
агрегация до 28 признаков — погрешность ≤ 3·10⁻¹⁵; |σ(decision_function) − сохранённый risk_score LogReg| ≤ 6·10⁻¹⁷.

**Pipeline:** `python -m orderpulse pipeline` на полном наборе — 112 с, без ошибок, 17/17 проверок витрин.

## 3. Ограничения (видны в README и в UI)

- Модель обучена на доставленных заказах; очередь — историческая симуляция.
- Development-оценка ретроспективна; исходный test — ранее просмотренный holdout.
- Найденные задержки не означают предотвращённые; эффект проверки не измерялся; K = 20 — компромисс, а не оптимум.
- Калибровки нет (осознанно); риск-скор — не вероятность.
- Механизм отбора в конце датасета неизвестен.
