# OrderPulse

[![CI](https://github.com/7SUNNY77/orderpulse/actions/workflows/ci.yml/badge.svg)](https://github.com/7SUNNY77/orderpulse/actions/workflows/ci.yml)

OrderPulse — приложение для аналитики доставки интернет-магазина. Оно показывает, где заказы опаздывают, и каждый
день составляет очередь новых заказов с самым высоким риском опоздания, чтобы менеджер проверял их первыми.

*English:* E-commerce delivery analytics and daily risk prioritization on the Olist dataset, with temporal
backtesting and interpretable ML. The app shows where deliveries run late and ranks each day's new orders by delay
risk, explaining every score. The UI and docs are in Russian.

## Что это и зачем

Менеджер успевает вручную проверить, скажем, 20 заказов в день, а заказов сотни. В момент подтверждения заказа
модель оценивает риск опоздания, и в очередь дня попадают 20 самых рискованных. Остальные страницы показывают,
где и почему задержки случаются чаще.

Данные — открытый набор бразильского маркетплейса Olist: около 100 тысяч анонимизированных заказов 2016–2018 годов.

## Как это выглядит

![Очередь риска](docs/screenshots/queue.png)

В приложении пять страниц:

- **Обзор** — число заказов, доля опозданий, сроки доставки по месяцам и связь опозданий с оценками покупателей.
  У каждой цифры подписано, от чего она посчитана.
- **Сегменты** — продавцы, регионы и категории, которые опаздывают чаще. Для маленьких сегментов виден интервал
  неопределённости.
- **Очередь риска** — 20 заказов с наибольшим риск-скором в каждый день (число настраивается), фильтры по штату,
  категории и продавцу, выгрузка в CSV. Фактические исходы по умолчанию скрыты, как и в реальной работе.
- **Карточка заказа** — детали заказа и вклады признаков в риск-скор: что его повысило, что понизило.
  Вклады в сумме дают ровно скор модели.
- **Качество** — как проверялась модель и как результат зависит от размера очереди.

## Результаты

Я проверял очередь на прошлых периодах: три окна с октября 2017 по март 2018, всего 182 дня и 37 872 заказа.
Перед каждым окном модели обучались заново только на более ранних данных.

| Отбор 20 заказов в день | Найдено опозданий в день | Доля опоздавших в очереди |
|---|---:|---:|
| Logistic Regression (основная модель) | 3,41 | 17,1% |
| CatBoost (для сравнения) | 2,74 | 13,8% |
| Случайный выбор | 1,92 | 9,7% |

Очередь находит опоздания примерно в 1,8 раза чаще случайного выбора (lift 1,773). CatBoost на этих данных оказался
хуже линейной модели на всех трёх окнах, поэтому основной я выбрал Logistic Regression.
Полные таблицы — в `experiments/reliability_v2/topk_dev.csv`.

![Очередь с исходами](docs/screenshots/queue_outcomes.png)

*Один день, 1 апреля 2018: с включёнными исходами видно, сколько опозданий нашла очередь по сравнению со случайным
выбором. За отдельный день цифры сильно скачут, общий результат — в таблице выше.*

## Как запустить

Нужны Python 3.11 и данные Olist. Данные в репозиторий не входят: скачайте
[Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)
и положите девять CSV в папку `data/`, не переименовывая. Если файлы лежат в другом месте:
`python -m orderpulse pipeline --raw-dir <папка>`. Сами CSV программа не меняет.

```bash
git clone https://github.com/7SUNNY77/orderpulse.git
cd orderpulse
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\Activate.ps1
python -m pip install -r requirements-lock.txt
python -m pip install -e ".[dev]"

python -m orderpulse pipeline      # сборка данных и моделей, около 2 минут
python -m orderpulse app           # http://localhost:8501
```

Если не хватает файлов, базы или моделей, команда пишет, чего именно. На Windows перед пересборкой закройте приложение.

Тесты не требуют настоящих данных: они генерируют небольшой искусственный набор заказов. В GitHub Actions они
запускаются на Ubuntu и Windows.

```bash
python -m pytest                        # все тесты
python -m pytest -m "not integration"   # без медленных: полного конвейера и страниц приложения
```

## Как устроено

```
CSV Olist → DuckDB (очистка и проверки) → таблица «один заказ = одна строка»
          → признаки на момент подтверждения → обучение модели → прогнозы → приложение на Streamlit
```

- **Данные.** CSV загружаются в DuckDB, чистятся и сводятся в витрины. Сборка проходит 17 проверок сверки сумм и
  числа строк, чтобы ничего не задвоилось и не потерялось; база заменяется только при успехе всех проверок.
- **Модель.** Logistic Regression на 28 признаках: состав и цена заказа, обещанный срок, расстояние, регион,
  категория, день недели. Признаки берутся только из того, что известно в момент подтверждения заказа;
  тесты проверяют, что изменение будущих событий не меняет признаки.
- **Проверка.** Обучение на прошлом, оценка на более позднем периоде, между ними месяц зазора. Каждый день очередь
  сравнивается со случайным выбором того же числа заказов.
- **Шаги конвейера** `ingest`, `quality`, `marts`, `train`, `evaluate`, `predict` запускаются и по отдельности:
  `python -m orderpulse <шаг>`.

```
app/          приложение на Streamlit (5 страниц)
src/          конвейер данных, обучение и оценка
sql/          SQL витрин и признаков
configs/      периоды выборок, параметры моделей, настройки интерфейса
tests/        тесты на синтетических данных
reports/      model card, отчёты о качестве данных и надёжности, журнал решений
experiments/  итоговые цифры проверки (CSV, JSON, графики)
```

## Ограничения

- Это симуляция на исторических данных, а не работа с живыми заказами.
- Найти опоздание не значит его предотвратить: эффект ручных проверок никто не измерял.
- Риск-скор нужен для порядка в очереди, это не вероятность: модель не откалибрована.
- Модель обучена только на доставленных заказах и не предсказывает отмены и потерянные посылки.
- Цифры в таблице результатов относятся к рецепту обучения, а не к одному сохранённому файлу модели.
- Период апрель–июнь 2018 я уже смотрел во время разработки, поэтому он не считается чистой проверкой.
  Там модель тоже лучше случайного выбора: 12,2% против 3,9%.
- Качество сильно зависит от периода: доля опозданий по неделям меняется от 0,3% до 11,8%.
- Размер очереди 20 — компромисс для демонстрации, а не доказанный оптимум.
- Состав заказа и обещанная дата считаются известными в момент подтверждения: журнала событий в данных нет.
- В конце набора среди поздних заказов нет опозданий, причина неизвестна; июль–август 2018 в оценке не участвуют.
- Вклады признаков описывают поведение модели, а не настоящие причины опозданий.

## Что можно улучшить

- Учитывать историю продавца: как часто он опаздывал раньше.
- Пересчитывать риск, когда заказ уже передан перевозчику.
- Предсказывать не «опоздает или нет», а сам срок доставки.
- Собирать данные о реальных проверках, чтобы понять, помогают ли они.
